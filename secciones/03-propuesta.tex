\section{Producto propuesto}
El producto de este proyecto es un proceso de integración y entrega continua para el sistema, diseñado para operar sobre 
la infraestructura autoalojada de la organización. Todos sus elementos se describen en archivos versionados dentro del repositorio 
(infraestructura como código), por lo que el proceso es repetible y queda registrado. Se compone de:

\begin{itemize}
    \item Las imágenes de contenedor de la aplicación y su configuración.
    \item Un \emph{pipeline} en GitLab que, en cada \emph{push}, construye la imagen, ejecuta el análisis estático del código y despliega un entorno de prueba.
    \item El mecanismo para crear el entorno de prueba de una rama, con la aplicación y sus dos bases de datos cargadas con datos de prueba.
    \item El despliegue automatizado a producción, que ejecuta en orden las migraciones de ambas bases de datos, limpia las cachés y verifica que la aplicación responda.
    \item La documentación de uso y el informe de evaluación frente al proceso manual actual.
\end{itemize}

El proceso funciona de la siguiente manera (Figura~\ref{fig:arquitectura_solucion}). Cuando un desarrollador
sube una rama al repositorio, GitLab inicia un \emph{pipeline} que construye la imagen de contenedor de la aplicacion
y ejecuta el análisis estático del código. Si el análisis se aprueba, el \emph{pipeline} despliega un entorno
 de prueba con esa rama. En ese entorno, el equipo realiza la validación funcional manual del cambio. Una vez validado, 
 se abre la solicitud de cambio, se revisa y se fusiona. Al fusionarse, el \emph{pipeline} despliega la aplicación 
 en producción [CONFIRMAR: de forma automática o tras una aprobación en GitLab].

 \begin{itemize}
    \item \textbf{Imágenes versionadas.} La misma imagen de contenedor se usa en desarrollo, pruebas y 
    producción, lo que reduce las diferencias de configuración entre ambientes.
    \item \textbf{Infraestructura autoalojada.} Todo el proceso opera en los servidores 
    de la organización, sin depender de servicios de nube pública.
    \item \textbf{Entorno de prueba bajo demanda.} Cada rama puede probarse en un entorno propio, con datos
    de prueba generados mediante \emph{seeders} que respeetan las relaciones entre MySQL y MongoDB. La validacion
    funcional sigue siendo manual: el entorno la hace posible y ordenada, pero no lo sustituye.
    \item \textbf{Despliegue coordinado de las dos bases de datos.} Las migraciones de ambos motores se ejecutan 
    en un orden definido y verificable. Como los mototres no comparten transacciones, el proceso asegura el orden
    y la verificacion, no la atomicidad

 \end{itemize}
