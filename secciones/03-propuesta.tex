\section{Producto propuesto}
El producto de este proyecto es un proceso de integración y entrega continua para el sistema, diseñado para operar sobre la infraestructura autoalojada de la organización. Todos sus elementos se describen en archivos versionados dentro del repositorio (infraestructura como código), por lo que el proceso es repetible y queda registrado. Se compone de:
\begin{itemize}
  \item Las imágenes de contenedor de la aplicación y su configuración.
  \item Un \emph{pipeline} en GitLab que, en cada cambio que se sube al repositorio, construye la imagen y ejecuta las compuertas de calidad.
  \item El despliegue de prueba bajo demanda: desde GitLab se elige una rama y una instancia de prueba, y se despliega ahí la aplicación con sus dos bases de datos, con la opción de aplicar migraciones y cargar datos de prueba.
  \item El despliegue a producción desde una rama de liberación, con aprobación manual, que ejecuta en orden las migraciones de ambas bases de datos y verifica que la aplicación responda.
  \item La documentación de uso y el informe de evaluación frente al proceso manual actual.
\end{itemize}

El proceso funciona de la siguiente manera (Figura~\ref{fig:arquitectura_solucion}).
Cuando un desarrollador sube una rama, GitLab inicia un \emph{pipeline} de revisión que
construye la imagen y ejecuta las compuertas de calidad. Si el desarrollador lo requiere,
puede desplegar su rama en una instancia de prueba para que el cambio se valide de forma
manual, de preferencia por quien lo usará. Cuando el cambio pasa las verificaciones y las
aprobaciones del equipo, se fusiona con la rama principal. Para llevarlo a producción se
crea una rama de liberación a partir de la principal; sobre ella se ejecuta el \emph{pipeline}
de despliegue, que vuelve a ejecutar las verificaciones y, tras una aprobación manual, despliega
la aplicación en producción.

Las características principales del proceso son:
\begin{itemize}
  \item \textbf{Imágenes versionadas.} Las imágenes de todos los ambientes se construyen a partir de la misma definición y de la misma imagen base, lo que reduce las diferencias de configuración entre ambientes.
  \item \textbf{Infraestructura autoalojada.} GitLab, su registro de contenedores y los servidores donde se despliega son propios y se administran internamente.
  \item \textbf{Despliegue de prueba bajo demanda.} Una instancia de prueba es un servidor interno
  donde se despliega la aplicación para validar un cambio. Cualquier integrante puede desplegar una
  rama en una de ellas, con datos de prueba generados mediante \emph{seeders} que respetan las relaciones
  entre MySQL y MongoDB. Las instancias son persistentes y cada una aloja una rama a la vez.
  La validación funcional sigue siendo manual: la instancia la hace posible y ordenada, pero no la sustituye.
  \item \textbf{Despliegue coordinado de las dos bases de datos.} Las migraciones de ambos motores se ejecutan en un orden definido y antes de exponer el código nuevo. Como los motores no comparten transacciones, el proceso asegura el orden y la verificación, no la atomicidad.
  \item \textbf{Controles en producción.} El despliegue requiere la aprobación manual de un rol autorizado y no permite borrar la base de datos.
\end{itemize}

\subsection{Métricas de aceptación}

Para determinar el éxito y la viabilidad del producto propuesto tras su implementación,
se establecen los siguientes criterios operativos, evaluados frente a la línea base histórica:

\begin{itemize}
\item \textbf{Reducción de pasos manuales:} El proceso de despliegue a producción debe reducirse a una
única aprobación manual (clic) en la interfaz de GitLab, delegando la construcción de imágenes,
ejecución de migraciones y verificación al \emph{pipeline} automatizado.

\item \textbf{Tiempo máximo de despliegue:} La ejecución del \emph{pipeline} de liberación a producción
deberá completarse de forma predecible y documentada, estandarizando el tiempo que toma colocar
el código en el servidor.

\item \textbf{Impacto en el \emph{lead time}:} La adopción del proceso automatizado y las compuertas
de calidad no deberá generar una degradación significativa en el \emph{lead time} mediano actual de 55 minutos,
demostrando que la automatización no es un cuello de botella.

\item \textbf{Porcentaje de despliegues exitosos:} Se busca disminuir la tasa histórica de fallos
(estimada actualmente en un máximo del 21.9\%) mediante la detección temprana de defectos en el \emph{pipeline}
de revisión y la validación en los entornos de prueba bajo demanda.
\end{itemize}

\section{Metodología}
Para llevar a cabo el desarrollo de este proyecto se optó por un enfoque basado en una metodología ágil adaptada
del marco de trabajo \emph{Scrum}, lo que permitirá una respuesta flexible ante los retos técnicos
inherentes a la intervención de sistemas \emph{legacy}. El trabajo se estructurará en iteraciones cortas
o \emph{sprints}, cuyas tareas, incidencias y avances serán gestionados a través de tableros para el control
del flujo de trabajo. De esta forma, cada incremento iterativo entregará una parte funcional y
medible de la automatización del \emph{pipeline}. Técnicamente, la ejecución se estructurará
en las siguientes seis fases progresivas:

\begin{itemize}
  \item \textbf{Fase 1. Diagnóstico y línea base}: Se realizará un levantamiento detallado del
  proceso de despliegue manual actual. Se extraerán las métricas históricas del repositorio en
  GitLab para consolidar la línea base cuantitativa, estableciendo la frecuencia de despliegue,
  el \emph{lead time} y la tasa de fallos actual.

  \item \textbf{Fase 2. Contenedorización}: Se empaquetará (\emph{dockerización}) la aplicación
  web. Para mantener el rendimiento del servidor CI, se diseñará una estrategia de construcción
  basada en imágenes de múltiples capas (separando la compilación de extensiones base del código
  de la aplicación). Se ejecutará una validación funcional para garantizar que el aislamiento
  del \emph{runtime} no altere la lógica de negocio ni la conexión entre los motores.

  \item \textbf{Fase 3. Pipeline CI y Compuertas de calidad}: Se configurará en GitLab CI el flujo
  automático de construcción de imágenes. Ante la ausencia histórica de una \emph{suite} de pruebas
  automatizadas, el \emph{pipeline} se enfocará inicialmente en implementar compuertas de calidad
  basadas en análisis estático y seguridad. Esto contemplará la validación de la sintaxis del código,
  la revisión estandarizada de estilo y el escaneo de vulnerabilidades en los contenedores,
  utilizando herramientas compatibles con el ecosistema actual del proyecto.
  Adicionalmente, se integrará e inicializará la base del \emph{framework} de pruebas dentro
  del contenedor de integración, sentando la infraestructura necesaria para que el equipo comience una
  adopción progresiva de pruebas en futuros desarrollos.

  \item \textbf{Fase 4. Entornos de prueba bajo demanda}: Se provisionarán entornos aislados para la aplicación en la infraestructura
  autoalojada, gestionados mediante herramientas como SSH y Docker Compose. Desde estos contenedores efímeros se automatizará la ejecución
  segura de migraciones y \emph{seeders} hacia las bases de datos correspondientes al entorno
  de pruebas, permitiendo validaciones manuales antes de la integración.

  \item \textbf{Fase 5. Pipeline CD (Entrega continua)}: Se automatizará la liberación a
  producción mediante un flujo protegido por aprobación manual en la plataforma.
  El despliegue automatizado garantizará la ejecución ordenada de las migraciones necesarias en
  MySQL y MongoDB correspondientes a la nueva versión de la aplicación, eliminando la necesidad
  de intervención manual por SSH.

  \item \textbf{Fase 6. Evaluación de Resultados}: Se comparará empíricamente el nuevo proceso
  automatizado frente a la línea base histórica obtenida en la Fase 1. Se determinará el cumplimiento
  de las métricas de aceptación y se documentará el impacto final en el \emph{lead time} y la tasa de errores.
\end{itemize}
