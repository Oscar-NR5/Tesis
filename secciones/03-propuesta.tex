\section{Producto propuesto}
El producto de este proyecto es un proceso de integración y entrega continua para el sistema, diseñado para operar sobre la infraestructura autoalojada de la organización. Todos sus elementos se describen en archivos versionados dentro del repositorio (infraestructura como código), por lo que el proceso es repetible y queda registrado. Se compone de:
\begin{itemize}
  \item Las imágenes de contenedor de la aplicación y su configuración.
  \item Un \emph{pipeline} en GitLab que, en cada cambio que se sube al repositorio, construye la imagen y ejecuta las compuertas de calidad.
  \item El despliegue de prueba bajo demanda: desde GitLab se elige una rama y una instancia de prueba, y se despliega ahí la aplicación con sus dos bases de datos, con la opción de aplicar migraciones y cargar datos de prueba.
  \item El despliegue a producción desde una rama de liberación, con aprobación manual, que ejecuta en orden las migraciones de ambas bases de datos y verifica que la aplicación responda.
  \item La documentación de uso y el informe de evaluación frente al proceso manual actual.
\end{itemize}

El proceso funciona de la siguiente manera (Figura~\ref{fig:arquitectura_solucion}). Cuando un desarrollador sube una rama, GitLab inicia un \emph{pipeline} de revisión que construye la imagen y ejecuta las compuertas de calidad. Si el desarrollador lo requiere, puede desplegar su rama en una instancia de prueba para que el cambio se valide de forma manual, de preferencia por quien lo usará. Cuando el cambio pasa las verificaciones y las aprobaciones del equipo, se fusiona a la rama principal. Para llevarlo a producción se crea una rama de liberación a partir de la principal; sobre ella se ejecuta el \emph{pipeline} de despliegue, que vuelve a correr las verificaciones y, tras una aprobación manual, despliega la aplicación en producción.

Las características principales del proceso son:
\begin{itemize}
  \item \textbf{Imágenes versionadas.} Las imágenes de todos los ambientes se construyen a partir de la misma definición y de la misma imagen base, lo que reduce las diferencias de configuración entre ambientes.
  \item \textbf{Infraestructura autoalojada.} GitLab, su registro de contenedores y los servidores donde se despliega operan en infraestructura de la organización.
  % TODO(tesis): decidir si el pipeline usa servicios externos y cómo se describen
  \item \textbf{Despliegue de prueba bajo demanda.} Una instancia de prueba es un servidor de la organización donde se despliega la aplicación para validar un cambio. Cualquier integrante puede desplegar una rama en una de ellas, con datos de prueba generados mediante \emph{seeders} que respetan las relaciones entre MySQL y MongoDB. Las instancias son persistentes y cada una aloja una rama a la vez. La validación funcional sigue siendo manual: la instancia la hace posible y ordenada, pero no la sustituye.
  \item \textbf{Despliegue coordinado de las dos bases de datos.} Las migraciones de ambos motores se ejecutan en un orden definido y antes de exponer el código nuevo. Como los motores no comparten transacciones, el proceso asegura el orden y la verificación, no la atomicidad.
  \item \textbf{Controles en producción.} El despliegue requiere la aprobación manual de un rol autorizado y no permite borrar la base de datos.
\end{itemize}
